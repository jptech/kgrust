## 0. Architectural fact you must absorb first: there is no lexer

The reference front end is a **scannerless** parser. It is `megaparsec` running directly over
`String` (`Parser' s e a = ReaderT Config (StateT SymbolTable (ParsecT e s Cache))`,
`compiler/hs/lib/Language/Kanagawa/Parser.hs:47-49`; the stream type is `String`, line 49).
There is no token type, no token stream, and no lexer/parser boundary. "Lexer.hs" is a module of
*lexeme combinators*, not a tokenizer.

Consequences that the Rust lexer must be designed around:

1. **Token boundaries are context-dependent.** The same characters `>>` are two template-list
   closers in one context and one shift operator in another (§12).
2. **Backtracking is pervasive.** Almost every lexeme combinator is wrapped in `try`
   (e.g. `Lexer.hs:236`, `246`, `262`, `273`), so a failed "token" costs nothing and the
   parser simply tries a different reading of the same characters.
3. **Identifier legality depends on a Haskell `Read` call** (`Lexer.hs:238-243`), not on a
   regular expression (§5.3).
4. **String literals are not tokens.** An interpolated string can contain arbitrary
   expressions, including *nested string literals* (§9.4). Verified:
   `test/syntax/interpolated-string.k:185-190` compiles `"{stringFun("{boolConst:b3}")}"`.
5. **Symbol resolution feeds back into parsing.** Whether `foo<...>` is a template
   instantiation depends on whether `foo` resolves to a template in the symbol table
   (`Parser.hs:658-684`). A pure Rust lexer cannot know this; the Rust *parser* must.

The Rust rewrite therefore needs a lexer that is deliberately **under-committed**: it must emit
the smallest tokens the reference can distinguish, plus enough adjacency information for the
parser to re-glue them. See §12 and §14.

## 2. Lexeme discipline (how trivia attaches)

The reference follows the standard megaparsec convention, made explicit at
`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:124-128`:

```haskell
lexeme = L.lexeme whitespace          -- Lexer.hs:125
symbol = L.symbol whitespace          -- Lexer.hs:128
```

Every lexeme **assumes no leading trivia and consumes all trailing trivia**. Leading trivia at
the start of the file is consumed once by `between whitespace eof` (`Parser.hs:108`).

This matters for the Rust rewrite because several constructs use *bare* `char`/`string` parsers
that do **not** skip trivia, and therefore impose adjacency requirements. Complete list of
trivia-insensitive (bare) parsers:

| Construct | Parser | Citation | Adjacency requirement |
|---|---|---|---|
| digits of `intN` / `uintN` | `string "int" <*> intSuffix` | `Parser.hs:542-543` | `int` and the digits must be adjacent |
| integer literal body | `integer` (not a lexeme itself) | `Lexer.hs:133-156`, wrapped at `Parser.hs:904` | all characters of a numeric literal adjacent |
| literal type suffix `i`/`u` + width | `string (show x) <*> L.decimal` | `Parser.hs:908` | suffix adjacent to the number, width adjacent to `i`/`u` |
| format precision after `b`/`o`/`d`/`x`/`X` | `optional L.decimal` inside one `L.lexeme` | `Parser.hs:900` | precision adjacent to the specifier char |
| opening `"` of a string | `char '"'` | `Parser.hs:883`, `Lexer.hs:162` | — |
| closing `}` of an interpolation hole | `char '}'` | `Parser.hs:888` | — |
| designated-initializer `.` | `char '.'` | `Parser.hs:863` | `.` adjacent to the field name |
| module-name dots | `sepBy1` on `char '.'` | `Lexer.hs:231` | no trivia around the dots |
| doc-comment prefix scan | `(string "//" <|> string "/*") *> hspace *> char prefix` | `Lexer.hs:82` | only *horizontal* space between `//` / `/*` and `|` / `<` |

By contrast, member access `a . b` **does** allow trivia around the dot, because it uses the
`dot` lexeme (`Lexer.hs:286`, used at `Parser.hs:814` and `Parser.hs:732`).

## 3. Whitespace

`whitespace` is selected by the `parseDocs` config flag (`Lexer.hs:94-119`):

```haskell
whitespace = do
    docs <- asks parseDocs
    if docs then whitespaceNonDoc     -- Lexer.hs:97
            else whitespaceAll        -- Lexer.hs:98
```

- Horizontal/vertical space: `L.space space1 ...` (`Lexer.hs:100`, `Lexer.hs:105`).
  `space1` in megaparsec is `takeWhile1P … isSpace`, i.e. **Unicode-aware `Data.Char.isSpace`**:
  `' '`, `\t`, `\n`, `\r`, `\f`, `\v`, plus every Unicode `Zs`/`Zl`/`Zp` character
  (`U+00A0`, `U+2000`–`U+200A`, `U+3000`, …).
  *Source of the predicate is the megaparsec library, not this tree — see §16 Q1.*
- `hspace` (used only in doc-comment scanning, `Lexer.hs:82`, `87`, `88`, `111`) is "like `space`
  but does not accept newlines and carriage returns" — i.e. `isSpace c && c /= '\n' && c /= '\r'`.
  *megaparsec library semantics; see §16 Q1.*

### 3.1 Are newlines significant?

**No.** There is no layout rule, no offside rule, no newline token, no semicolon insertion, and
no line-continuation escape anywhere in `Lexer.hs` or `Parser.hs`. Newlines are ordinary
whitespace. The only three places a newline has *any* meaning:

1. It terminates a `//` line comment (`Lexer.hs:102`, `Lexer.hs:114`, `Lexer.hs:87`).
2. It terminates one line of a doc line-comment run; `hspace` (not `space`) is used between
   consecutive `//` lines, so a **blank line ends a doc-comment run** (`Lexer.hs:87`).
   Verified: `test/syntax/doc-comments.k:203-208` — a blank line between two `//|` runs is a
   compile error (`expected:1`).
3. Statements are terminated by `;`, never by newline (`Lexer.hs:283`, used throughout
   `Parser.hs`, e.g. `Parser.hs:246`, `276`, `299`, `569`).

### 3.2 Is there a preprocessor?

**No.** Grep of the whole compiler for `#`-directives finds only `hash = symbol "#"`
(`Lexer.hs:288`), which is **exported but never called** — `hash` appears at `Lexer.hs:37`
(export list), `Lexer.hs:282` (type signature) and `Lexer.hs:288` (definition) and nowhere else
in the tree. So `#` is **never a legal character in Kanagawa source outside comments and string
literals**. Confirmed empirically: every `#` in `library/**.k` and `test/**.k` is inside a
comment or a string (e.g. `library/processor/risc_v.k:21` is Markdown inside a doc comment).

`--define` / `--using` are *not* preprocessor directives. They are command-line options
(`compiler/hs/app/Options/CmdArgs.hs:63-64`, `typ "name#val"`) whose values are textually
spliced into a synthesized module named `.cmdargs`
(`compiler/hs/lib/Language/Kanagawa/Parser/IO.hs:37-55`):

```haskell
buildCmdargsSpecialModule opt =
    buildModule cmdargsSpecialModule [] (nameValue <$> define opt) (nameValue <$> using opt)
  where
    nameValue (x:xs') | x == '#' || x == '=' = ([], xs')   -- IO.hs:54
```

So `--define=ELEVEN#11` (used at `test/syntax/CMakeLists.txt:82`) generates the source text
`const auto ELEVEN = 11;` inside module `.cmdargs`, which is then lexed normally. The separator
may be `#` **or** `=` (`Parser/IO.hs:54`). `--using name#type` generates `using name = type;`
(`Parser/IO.hs:42-43, 50`).

## 4. Comments

### 4.1 The four comment kinds and their relation to doc comments

| Form | Nesting | Meaning | Citation |
|---|---|---|---|
| `// …⏎` | n/a | ordinary line comment | `Lexer.hs:102`, `Lexer.hs:113-114` |
| `/* … */` | **nested** | ordinary block comment | `Lexer.hs:103`, `Lexer.hs:116-119` |
| `//\|` … | n/a | doc comment for the **following** declaration | `Lexer.hs:64`, `Lexer.hs:91` |
| `//<` … | n/a | doc comment for the **preceding** declaration | `Lexer.hs:65`, `Lexer.hs:92` |
| `/*\| … */` | **NOT nested** | doc comment for the **following** declaration | `Lexer.hs:88`, `Lexer.hs:64` |
| `/*< … */` | **NOT nested** | doc comment for the **preceding** declaration | `Lexer.hs:88`, `Lexer.hs:65` |

The prefix characters are named constants:

```haskell
docCommentPrefixPre  = '|'      -- Lexer.hs:64
docCommentPrefixPost = '<'      -- Lexer.hs:65
```

### 4.2 Nesting: verified both ways

Ordinary block comments nest, via `L.skipBlockCommentNested "/*" "*/"`
(`Lexer.hs:103`, and `Lexer.hs:119` for the doc-enabled path).
Verified by test: `test/syntax/doc-comments.k:144-151` (`/* /* nested comment */ */` →
`expected:0`) and documented at `doc/programming-guide.md:38-42`.

Doc block comments **do not nest**: `blockComment = string "/*" *> manyTill anySingle (string "*/")`
(`Lexer.hs:88`) stops at the *first* `*/`. Verified by test:
`test/syntax/doc-comments.k:135-142` — a `/*| … /* nested */ … */` is `expected:1` (error),
with the test's own comment text reading "nested comment not allowed in doc comment".

A doc-prefixed block comment **inside** an ordinary block comment is skipped as an ordinary
nested comment: `test/syntax/doc-comments.k:153-160` → `expected:0`, because
`skip = L.skipBlockCommentNested start end <|> void anySingle` (`Lexer.hs:119`) matches `/*`
unconditionally.

### 4.3 `parseDocs = False` (the default)

`parseDocs` defaults to `False` (`compiler/hs/lib/Language/Kanagawa/Parser/Options.hs:43`) and is
turned on by `--parse-docs` (`compiler/hs/app/Options/CmdArgs.hs:67`). It is threaded into the
lexer as `Config{parseDocs}` (`Lexer.hs:67-73`, constructed at `Parser/IO.hs:94`).

When `parseDocs = False`, **all four comment forms are plain trivia** — `whitespaceAll` uses
`L.skipLineComment "//"` and `L.skipBlockCommentNested "/*" "*/"` with no prefix inspection
(`Lexer.hs:100-103`), and `docCommentPre`/`docCommentPost` return `[]` without consuming anything
(`Lexer.hs:77-79`).

> **This is the single most important fact for the Rust lexer:** doc comments are *not* a
> separate lexical class in the default configuration. A Rust lexer that always classifies
> `//|` as `DOC_LINE_COMMENT_PRE` is still correct provided the parser treats it as ordinary
> trivia unless doc parsing is enabled.

### 4.4 `parseDocs = True`: trivia excludes doc comments

`whitespaceNonDoc` (`Lexer.hs:105-119`) refuses to skip any comment whose introducer is followed
(after `hspace`) by `|` or `<`:

```haskell
startNonDocComment prefix =
    try (string prefix *> hspace *> notFollowedBy (char docCommentPrefixPre <|> char docCommentPrefixPost))
                                                                        -- Lexer.hs:110-111
```

So with `--parse-docs`, a doc comment that is *not* consumed by `docCommentPre`/`docCommentPost`
becomes a hard parse error. Verified: `test/syntax/doc-comments.k:162-165` (`//<` before a
declaration → `expected:1`), `:167-170` (`//|` after the last declaration → `expected:1`),
`:111-113` (`//|` alone → `expected:1`), `:123-129` (`/*| */` and `/*< */` alone → `expected:1`).
An ordinary `//` or `/* */` alone is fine (`:119-121`, `:131-133` → `expected:0`).

### 4.5 The doc-comment run grammar

```haskell
docComment prefix = ... lexeme docComment' ...                 -- Lexer.hs:78
  where
    docComment' = do
        hasDocPrefix <- isJust <$> optional (lookAhead $ try
            ((string "//" <|> string "/*") *> hspace *> char prefix))   -- Lexer.hs:82
        if hasDocPrefix
          then many $ (LineComment <$> some lineComment)
                  <|> (BlockComment . lines <$> blockComment)           -- Lexer.hs:84
          else return mempty
    lineComment  = string "//" *> manyTill anySingle (char '\n') <* hspace   -- Lexer.hs:87
    blockComment = string "/*" *> manyTill anySingle (string "*/") <* hspace -- Lexer.hs:88
```

Derived rules, each verified by test:

1. **The prefix is only checked once, at the head of the run.** After a run starts, *every*
   following comment — doc-prefixed or not — is absorbed until a non-comment character.
   Verified: `test/syntax/doc-comments.k:172-179` (`//| multi` / `//< line` / `/*| … */` before
   one `struct` → `expected:0`; the `//<` is swallowed into the *pre* docs) and
   `test/syntax/doc-comments.k:181-189` / `:191-201` (a plain `/* … */` after a doc run is
   absorbed, `expected:0`). Also `doc/programming-guide.md:50-52` shows `//|` followed by plain
   `//` continuation lines.
2. **Horizontal space is allowed between the introducer and the prefix char.**
   `// | text` and `// < text` are doc comments (`Lexer.hs:82`, `hspace`). Verified:
   `test/syntax/doc-comments.k:23` (`// < post class template Foo`),
   `test/syntax/doc-comments.k:35-37` (`// |` then `// pre global const Foo`),
   `test/syntax/doc-comments.k:43-45` (`// < post …`).
3. **Consecutive `//` lines join into one `LineComment`** (`some lineComment`, `Lexer.hs:84`);
   `<* hspace` (`Lexer.hs:87`) means the next line may be indented.
4. **A blank line terminates the run**, because `hspace` cannot cross `\n`. Verified:
   `test/syntax/doc-comments.k:203-208` and `:210-215` → `expected:1`.
   (Counter-example: a blank line *inside* a `/*| … */` is fine — `:191-201` → `expected:0`.)
5. **The prefix character is retained in the captured text.** `manyTill anySingle` starts
   immediately after `//` or `/*` (`Lexer.hs:87-88`), so the payload of the first line is
   `"| pre param N "` etc. The consumer strips it:
   `stripDocPrefix … l' = tail $ dropWhile isSpace l`
   (`tools/sandcastle/lib/Sandcastle/DocGen.hs:1021-1030`).
   `unpackDocComment` additionally drops one leading space per line for `LineComment`
   (`tools/sandcastle/lib/Sandcastle/DocGen.hs:973-981`).

### 4.6 Where doc comments attach

`notedWithDocs` is the only attachment mechanism (`Parser.hs:91-96`):

```haskell
notedWithDocs parser = do
    docPre  <- docCommentPre         -- Parser.hs:93   (prefix '|', before the node)
    (NotedExp n e) <- noted parser   -- Parser.hs:94
    docPost <- docCommentPost        -- Parser.hs:95   (prefix '<', after the node)
    return $ NotedExp (n {docs = (docPre, docPost)}) e
```

Complete list of `notedWithDocs` call sites — i.e. **the complete list of syntactic positions
where a doc comment may legally appear**:

| Position | Citation |
|---|---|
| every element of a `many`-list (top-level decls, class members, statements, switch blocks) | `Parser.hs:114` |
| every element of a `sepBy`-list (function parameters, lambda captures, initializer entries) | `Parser.hs:115` |
| every element of a `sepEndBy`-list (struct/union members) | `Parser.hs:117` |
| module `exposed` list entries (`module X`, `module X \ Y`, plain identifier) | `Parser.hs:187`, `191`, `192` |
| enum constants | `Parser.hs:290` (via `symbolWithDocs`, `Parser.hs:161`) |
| template parameters | `Parser.hs:362` |

Note `sepBy1` (`Parser.hs:116`) uses plain `noted`, **not** `notedWithDocs` — so no docs there.
And `template` declarations wrap their inner declaration with plain `noted`
(`Parser.hs:375`), which is why `test/syntax/doc-comments.k:224-230` (a `//|` between
`template <…>` and `class`) is `expected:1`.

### 4.7 Traps in comment lexing

- **A doc *line* comment at EOF with no trailing newline fails.** `lineComment` requires
  `char '\n'` (`Lexer.hs:87`); a plain line comment does not (`takeWhileP … (/= '\n')`,
  `Lexer.hs:114`). **UNVERIFIED by a test in this tree** — see §16 Q4.
- **`\r` leaks into doc text.** With CRLF files, `manyTill anySingle (char '\n')`
  (`Lexer.hs:87`) captures the `\r`. **UNVERIFIED by a test in this tree** — see §16 Q5.
- `skipBraces` (`Lexer.hs:121-122`) reuses `L.skipBlockCommentNested "{" "}"` to skip a class or
  function body during look-ahead (`Parser.hs:338`, `Parser.hs:423`). It counts raw `{`/`}`
  characters and is **blind to strings and comments**, so a `}` inside a string literal or a
  comment inside a skipped body will mis-balance it. Its callers wrap it in
  `optional . lookAhead . try` (`Parser.hs:307-309`), so a failure degrades to "no symbols
  pre-registered" rather than an error.

## 5. Identifiers

### 5.1 Character classes

```haskell
isAlphaNumOrUnderscore c = Char.isAlphaNum c || c == '_'      -- Lexer.hs:222
ident' f = (:) <$> (letterChar <|> char '_') <*> takeWhileP (Just "rest of identifier") f
                                                              -- Lexer.hs:225
ident = ident' isAlphaNumOrUnderscore                         -- Lexer.hs:228
```

- **Start**: `letterChar` (megaparsec = `Data.Char.isLetter`, Unicode categories
  `Lu Ll Lt Lm Lo`) **or** `_`.
- **Continue**: `Data.Char.isAlphaNum` (Unicode `Lu Ll Lt Lm Lo Nd Nl No`) **or** `_`.
- **Case sensitive** — no case folding anywhere; `char'` (case-insensitive) is used only for
  numeric base prefixes (`Lexer.hs:136`).
- **No length limit at lex time.** (`--identifier-length` at
  `compiler/hs/app/Options/CmdArgs.hs:73` truncates *generated output* names, not source
  identifiers.)

Unicode-awareness is a real difference from ASCII-only rules: `π`, `Ω`, `x²` (`U+00B2` is `No`,
so legal as a *continue* char) are all accepted. **The reference corpus contains no non-ASCII
identifier** — the only non-ASCII bytes in any `.k` file in `library/` or `test/` are two
`U+2011` non-breaking hyphens inside comments
(`library/device/ultrascaleplus-xcu250/hardware/config.k:7` and `:17`).

### 5.2 No reserved prefixes

There is **no** `__`, `_`, `$`, or other reserved-prefix rule in the lexer. `__print`,
`__cycles`, `__str_cnt`, `__assert_str_eq` are ordinary identifiers that the *type checker*
recognizes as intrinsics (`compiler/hs/lib/Language/Kanagawa/Type.hs:1079-1083`); they are used
as ordinary calls in the library (`library/debug/print.k:21`, `library/base/system.k:12`,
`library/test/internal/assert.k:57`).

Compiler-internal synthesized names use sigils that **cannot be written in source** and therefore
can never collide with user identifiers:

| Sigil form | Purpose | Citation |
|---|---|---|
| `$` | function scope marker | `Parser.hs:127` |
| `$quasi<N>` | anonymous block scope | `Parser.hs:133`, `Parser.hs:153` |
| `$this` | implicit object | `Parser/Syntax.hs:267-268` |
| `$unresolved` | unresolved-name placeholder | `Parser/Syntax.hs:270-271` |
| `$export<N>` | export decl name | `Parser/SymbolTable.hs:213` |
| `?lambda<N>` | lambda name | `Parser.hs:434` |
| `@…` | mangled module namespace | `Parser/Syntax.hs:273-274` |

### 5.3 The `intN` / `uintN` identifier exclusion (a `Read` call, not a regex)

```haskell
name = fromString <$> (lexeme . try) (ident >>= check) <?> "identifier"   -- Lexer.hs:236
  where
    check x = if x `Set.member` reserved || intType x
                then unexpected . Label . NE.fromList $ ("keyword " ++ show x)
                else return x                                             -- Lexer.hs:238-240
    intType ('i':'n':'t':x)     = isJust (readMaybe x :: Maybe Word)      -- Lexer.hs:241
    intType ('u':'i':'n':'t':x) = isJust (readMaybe x :: Maybe Word)      -- Lexer.hs:242
    intType _ = False                                                     -- Lexer.hs:243
```

An identifier is rejected if it is a reserved word **or** if it is `int`/`uint` followed by a tail
that Haskell's `Read Word` instance accepts. Because Haskell's numeric `Read` understands
base prefixes, the rejected set is larger than "`int` + decimal digits":

| Identifier | Legal? | Why |
|---|---|---|
| `int32`, `uint7`, `int007` | **rejected** | tail reads as `Word` |
| `int0x1F`, `int0X1f`, `uint0o17`, `int0b1011` | **rejected** | Haskell `Read` accepts `0x/0X/0o/0O/0b/0B` prefixes |
| `int32_t`, `uint8_x`, `interrupt`, `uintptr` | legal | tail does not read as `Word` |
| `int1e5`, `int1.5` | legal | `Text.Read.Lex.numberToInteger` returns `Nothing` for a `Number` with an exponent or fraction |
| `int`, `uint` | reserved words (§6), not caught by `intType` | tail is `""`, `readMaybe "" = Nothing` |

The `0x/0o/0b` cases are a real behavioural cliff: `int0x1F` is neither a type (the `intSuffix`
path fails, §7.1) nor an identifier, so it is a hard parse error with the message
`keyword "int0x1F"`. **The `0x/0o/0b` rejection is derived from GHC's `Text.Read.Lex.lexBaseChar`
semantics, which are not in this tree — see §16 Q2.** The decimal case is verified indirectly:
`int32`/`uint32` are used pervasively as types (e.g. `library/base.k`, `test/syntax/basics.k`)
and never as identifiers.

### 5.4 `dotSepName` — a *different*, laxer identifier used for module paths

```haskell
dotSepName = lexeme $ try (ident' isAlphaNumOrDashOrUnderscore `sepBy1` char '.')  -- Lexer.hs:231
  where isAlphaNumOrDashOrUnderscore c = isAlphaNumOrUnderscore c || c == '-'      -- Lexer.hs:233
```

Differences from `name`:

- `-` (hyphen-minus) is a legal **continue** character. Verified:
  `library/mini-base.k:12` (`module mini-base`), `library/intel/arria-10/config.k:9`
  (`module intel.arria-10.config`).
- Segments are separated by a **bare** `char '.'` — no trivia allowed around the dots.
- **No reserved-word check and no `intN` check.** `import int32.foo` would lex.
- Used only for `import`/`module` paths: `moduleName` (`Parser.hs:179-183`),
  `parseImports` (`Parser.hs:196`), `moduleIdentifier`/`moduleDiff` (`Parser.hs:191-192`).

### 6.2 Keyword boundary rule

```haskell
keyword' s = void $ lexeme $ try (string s <* notFollowedBy (alphaNumChar <|> char '_'))
                                                                        -- Lexer.hs:246
```

A keyword must not be immediately followed by a Unicode alphanumeric or `_`. So `static_assert`
is one keyword and never `static` + `_assert`; `intx` is an identifier, not `int` + `x`.
Note `alphaNumChar` is Unicode-aware, matching §5.1.

## 7. Reserved and contextual forms that are not in the keyword list

### 7.1 `intN` / `uintN` (fixed-width spellings) — the two-part parse

```haskell
type''' = choice
    [ Boolean  <$ keyword "bool"                                 -- Parser.hs:540
    , Float    <$ keyword "float32"                              -- Parser.hs:541
    , try (Integer  <$ string "int"  <*> intSuffix)               -- Parser.hs:542
    , try (Unsigned <$ string "uint" <*> intSuffix)               -- Parser.hs:543
    , ParamInt  <$ keyword "int"  <*> angles expressionTemplate    -- Parser.hs:544
    , ParamUint <$ keyword "uint" <*> angles expressionTemplate    -- Parser.hs:545
    , ... ]
intSuffix = lexeme (L.decimal <* notFollowedBy (alphaNumChar <|> char '_'))  -- Lexer.hs:259
```

Rules:

- `intN` / `uintN` require the digits to be **immediately adjacent** to `int`/`uint`
  (`string "int"` is not a lexeme, `Parser.hs:542`). `int 32` is **not** a type.
- The width is `L.decimal` — ASCII decimal digits only, **no `_` separators**, leading zeros
  allowed (`int007` ≡ `int7`). Result type is Haskell `Int`; megaparsec's `decimal` performs
  **no range check**, so an absurd width silently wraps (§15).
- `notFollowedBy (alphaNumChar <|> char '_')` (`Lexer.hs:259`) means `int32_t` and `int32x` fall
  through to the identifier path (and are legal identifiers, §5.3).
- `int<…>` / `uint<…>` take a full `expressionTemplate` inside `angles` — i.e. the
  restricted operator table (§11.2). Verified in use: `library/type/stdtype.k:13`
  (`using index_t = uint<(N > 1) ? clog2(N) : 1>;`), `library/codec/crc.k:63`
  (`reverse<uint<Width>>(Init)`), `doc/programming-guide.md:76-80`.
- `int`/`uint` alone, without digits and without `<`, is a parse error at the type level; both
  are reserved so they cannot be identifiers either.

**Rust lexing recommendation:** emit `INT_TYPE` / `UINT_TYPE` as single tokens whose text is
`int`/`uint` + digits, satisfying the boundary rule. Emit `INT_KW`/`UINT_KW` for the bare
keyword. Emit `IDENT` for `int`/`uint` + non-numeric tail, but reject (as an error token) the
`readMaybe`-positive base-prefixed forms of §5.3.

## 8. Numeric literals

### 8.1 Integers

```haskell
integer = (try hexadecimal <|> try binary <|> try octal <|> decimal) <?> "integer"  -- Lexer.hs:134
  where
    prefix x    = char '0' >> char' x >> optional (char '_')       -- Lexer.hs:136
    binary      = prefix 'b' >> integerRadix 2  isBinDigit         -- Lexer.hs:138
    octal       = prefix 'o' >> integerRadix 8  Char.isOctDigit    -- Lexer.hs:139
    hexadecimal = prefix 'x' >> integerRadix 16 Char.isHexDigit    -- Lexer.hs:140
    decimal     = integerRadix 10 Char.isDigit                     -- Lexer.hs:141

    integerRadix radix isDigit = do
        xs <- tokenList <$> takeWhile1P Nothing isDigit              -- Lexer.hs:148
        ys <- tokenList <$> takeWhileP  Nothing isDigitOrUnderscore  -- Lexer.hs:149
        return $ foldl' step 0 $ xs <> ys                            -- Lexer.hs:150
      where
        step a w | w == '_'  = a
                 | otherwise = a * radix + fromIntegral (Char.digitToInt w)  -- Lexer.hs:153-155
        isDigitOrUnderscore w = w == '_' || isDigit w                -- Lexer.hs:156
```

Grammar (ABNF-ish; `_` never contributes to the value):

```
integer      = hex / bin / oct / dec
hex          = "0" ("x" / "X") ["_"] HEXDIGIT *( HEXDIGIT / "_" )
bin          = "0" ("b" / "B") ["_"] BINDIGIT *( BINDIGIT / "_" )
oct          = "0" ("o" / "O") ["_"] OCTDIGIT *( OCTDIGIT / "_" )
dec          =                       DIGIT    *( DIGIT    / "_" )
```

Precise consequences (each with evidence):

- **Base prefixes are case-insensitive** — `char'` at `Lexer.hs:136` (`0x`/`0X`, `0b`/`0B`,
  `0o`/`0O`). No uppercase prefix occurs anywhere in `library/` or `test/`, so this path is
  exercised only by construction.
- **Exactly one optional `_` may follow the base prefix** (`optional (char '_')`, `Lexer.hs:136`).
  Verified: `0x_1234_abcd` (`test/syntax/literals.k:76`), `0b_0000_0000`
  (`test/syntax/literals.k:4`), `0o_2_215_125_715` (`test/syntax/literals.k:84`).
  Two underscores (`0x__1`) fall out of the hex branch entirely — §15 trap 3.
- **The first digit after the prefix must be a digit, not `_`** (`takeWhile1P`, `Lexer.hs:148`).
- **Trailing `_` is legal.** `100_000_` and `0o_100_000_` and `0x_100_000_` are all
  `expected:0` (`test/syntax/literals.k:96-98`, `:104-106`, `:112-114`); `0b0_` too
  (`test/syntax/literals.k:64-66`).
- **A leading `_` makes it an identifier, not a number** — `_100_000` is `expected:1`
  ("undefined symbol") at `test/syntax/literals.k:92-94`.
- **`0b` and `0b_` with no digits are errors** (`test/syntax/literals.k:68-74`, `expected:1`) —
  the binary branch fails and `decimal` matches just the `0`, leaving `b` / `b_` as a stray
  identifier.
- Digit predicates are `Data.Char.isDigit` / `isOctDigit` / `isHexDigit`, all **ASCII-only** in
  Haskell — Unicode digits are not accepted in numbers even though they are legal identifier
  continue characters (§5.1).
- **The value is arbitrary precision**: `IntLiteralF { literalValue :: Integer }`
  (`Parser/Syntax.hs:347-350`). Verified by `test/syntax/literals.k:44` which asserts a 60-bit
  binary literal equals `0xf00000000000008`.

### 8.2 Integer literal type suffix

```haskell
intLiteral = L.lexeme $ do
    x <- integer                                                        -- Parser.hs:905
    IntLiteral <$> optional (typeSuffix SignedLiteral <|> typeSuffix UnsignedLiteral) <*> pure x
                                                                        -- Parser.hs:906
  where
    typeSuffix x = LiteralType x <$ string (show x) <*> L.decimal        -- Parser.hs:908
```

Exact grammar:

```
int-literal   = integer [ suffix ]
suffix        = ( "i" / "u" ) 1*DIGIT          ; ASCII decimal, no "_" inside the width
```

- `show SignedLiteral = "i"`, `show UnsignedLiteral = "u"` (`Parser/Syntax.hs:223-225`).
  Signed is tried first (`Parser.hs:906`).
- The suffix must be **adjacent** to the number, but the number's own trailing `_` separates
  them naturally: `-10_i32` is legal (`test/syntax/literals.k:141-142`, `expected:0`), as are
  `0x100_u8` / `0x100u8` (`test/syntax/literals.k:156-157`), `0xFF_u8` / `0xFFu8`
  (`:161-162`), `0x80_i8` / `0x80i8` (`:166-167`), `0x7F_i8` / `0x7Fi8` (`:171-172`).
- **The width has no trailing-boundary check** (`Parser.hs:908` has no `notFollowedBy`), unlike
  `intSuffix` (`Lexer.hs:259`). So `10i32abc` lexes as `10i32` followed by identifier `abc`.
  **UNVERIFIED by test — see §16 Q6.**
- **A bare `i` or `u` with no width is a hard error, not a fallback.** `optional` is not wrapped
  in `try` (`Parser.hs:906`), so once `string "i"` consumes a character the failure of
  `L.decimal` propagates. **UNVERIFIED by test — see §16 Q7.**
- Width is Haskell `Int` (`LiteralType { literalWidth :: Int }`, `Parser/Syntax.hs:219`) from
  `L.decimal` with **no range check**.
- `i0` / `u0` lex fine and fail later, semantically: `10i0` and `10u0` are `expected:1`
  (`test/syntax/literals.k:116-122`).
- Range checking against the declared width is semantic, not lexical: `0x100u8` is
  `expected:1` while `0xFFu8` is `expected:0` (`test/syntax/literals.k:156-164`);
  `doc/programming-guide.md:113-118`.
- The `-` in `-10i32` is the **unary `Neg` operator**, not part of the literal
  (`Parser.hs:922`, `Parser.hs:964`; `doc/programming-guide.md:109`).

Hexadecimal never collides with the suffix letters: neither `i` nor `u` is a hex digit.

### 8.3 Floats

```haskell
float = lexeme L.float                                    -- Lexer.hs:159
literal = choice [ try $ FloatLiteral <$> float, intLiteral, ... ]   -- Parser.hs:879-880
```

`L.float` parses "a floating point number according to the syntax for floating point literals
described in the Haskell report" and, since megaparsec 6.1.1, **does not accept a plain
integer**. Grammar:

```
float    = 1*DIGIT ( fraction [exponent] / exponent )
fraction = "." 1*DIGIT
exponent = ("e" / "E") ["+" / "-"] 1*DIGIT
```

Therefore:

- `1.5`, `1.5e10`, `1.5E-3`, `1e10` are floats.
- `1.` is **not** (needs digits after the dot); `.5` is **not** (needs a leading digit);
  `1` is not (falls through to `intLiteral`, which is why `try` wraps it at `Parser.hs:879`).
- **No `_` digit separators in floats** — `L.float` does not accept them, unlike `integer`
  (§8.1). **UNVERIFIED by test — see §16 Q8.**
- **No suffix** (`f`, `F`, `d`) is accepted.
- Sign is the unary `Neg` operator, not part of the literal (`L.float` does not parse signs).

*The `L.float` grammar is megaparsec library semantics, not in this tree — see §16 Q1.*

**Value type is single precision**: `FloatLiteralF Float` (`Parser/Syntax.hs:352`) — Haskell
`Float`, IEEE binary32. This is *not* arbitrary precision, in deliberate contrast to
`IntLiteralF … Integer` (`Parser/Syntax.hs:349`). Matches the language having `float32` but no
`float64` builtin (`Parser.hs:541`; `tools/editors/vscode/GRAMMAR.md:266`).

Float literals in the corpus: `0.0`, `0.5`, `0.0625`, `1.10010010000111`, `0.86323547363` etc.
(`library/numeric/**.k`). No exponent form and no `_` occurs in any float in `library/` or
`test/`.

## 9. Character and string literals

### 9.1 There are no character literals

`'` is never a delimiter. Grep of `library/**.k`: every `'` is inside a comment or inside a
string literal (`library/data/string.k:182` is `return "'{x}'";`). No `char`-literal parser
exists in `Lexer.hs` or `Parser.hs`.

### 9.2 Two distinct string parsers

| Parser | Produces | Where used |
|---|---|---|
| `stringLiteral = lexeme (char '"' >> manyTill L.charLiteral (char '"'))` (`Lexer.hs:162`) | plain `String`, **no interpolation** | attribute string arguments only: `strAttr` (`Parser.hs:177`), via `strLiteral` (`Parser.hs:821`) → `[[name("…")]]` on class variables (`Parser.hs:462`), `export` (`Parser.hs:278`), `extern` (`Parser.hs:280`) |
| `InterpolatedString <$ char '"' <*> stringSegments <* L.symbol "\""` (`Parser.hs:883`) | `InterpolatedStringF [(String, Maybe (expr, Bool, Maybe expr, Maybe Format))]` (`Parser/Syntax.hs:358`) | **every string in expression position** |

So: **interpolation is legal in exactly one place — an expression-position string literal.**
It is *not* legal in `[[name("…")]]`. Note that `StringLiteralF` (`Parser/Syntax.hs:356`) is
produced only by the attribute path; an ordinary `"abc"` in an expression becomes an
`InterpolatedString` with a single text segment and no holes.

### 9.3 Escapes

Both paths use megaparsec's `L.charLiteral` (`Lexer.hs:162`, `Parser.hs:892`), documented as
parsing "a single literal character … according to the grammar rules defined in the Haskell
report". Its implementation dispatches to `Data.Char.readLitChar` over a bounded look-ahead
window of **up to 10 characters** (`count' 1 10`).

Escapes are therefore **Haskell escapes, not C escapes**:

| Class | Forms |
|---|---|
| Single-char | `\a \b \f \n \r \t \v \\ \" \' ` |
| Decimal numeric | `\` 1*DIGIT — e.g. `\65` is `A` |
| Hex numeric | `\x` 1*HEXDIGIT — e.g. `\x41` |
| Octal numeric | `\o` 1*OCTDIGIT — e.g. `\o101` |
| ASCII mnemonics | `\NUL \SOH \STX \ETX \EOT \ENQ \ACK \BEL \BS \HT \LF \VT \FF \CR \SO \SI \DLE \DC1 \DC2 \DC3 \DC4 \NAK \SYN \ETB \CAN \EM \SUB \ESC \FS \GS \RS \US \SP \DEL` |
| Control | `\^A` … `\^Z`, `\^@`, `\^[`, `\^\`, `\^]`, `\^^`, `\^_` |
| Empty escape | `\&` (produces nothing) |
| String gap | `\` *whitespace* `\` |

Notably **`\0` works** (decimal escape), **`\e` does not** (not a Haskell escape), and
**`\{` does not** — so a literal `{` must be written `{{` (§9.4), never `\{`.

*This list is Haskell-report/`readLitChar` semantics; the megaparsec source is not in this tree
— see §16 Q3.* Escapes actually exercised by the corpus: `\n` (579×), `\t` (21×), `\"` (6×),
`\r` (4×) across `library/**.k` and `test/**.k`; e.g. `library/debug/print.k:41`
(`__print("{x}\n")`), `library/processor/risc_v/trace.k:201`
(`asm = "{instr}\t{rd}, 0x{imm >> 12:x0}";`).

### 9.4 Interpolated strings — exact grammar

```haskell
InterpolatedString <$ char '"' <*> stringSegments <* L.symbol "\""       -- Parser.hs:883
  where
    stringSegments = do
        str <- manyTill charLiteral $ lookAhead (char '"' <|> try singleBrace)  -- Parser.hs:887
        fe  <- optional $ between (L.symbol "{") (char '}') formatedExpr        -- Parser.hs:888
        xs  <- (lookAhead (char '"') >> pure []) <|> stringSegments             -- Parser.hs:889
        return $ (str, fe) : xs                                                 -- Parser.hs:890
      where
        charLiteral = char '{' *> MP.charLiteral <|> MP.charLiteral             -- Parser.hs:892
        singleBrace = char '{' <* notFollowedBy (char '{')                      -- Parser.hs:893
    formatedExpr = do
        e <- expression                     -- Parser.hs:895
        n <- optional equal                 -- Parser.hs:896   ('=')
        a <- optional (comma >> expression) -- Parser.hs:897   (',' alignment)
        f <- optional (colon >> format)     -- Parser.hs:898   (':' format)
        return (e, isJust n, a, f)          -- Parser.hs:899
    format = L.lexeme $ Format <$> choiceViaShow [Bin, Oct, Dec, Hex, HexUpper] <*> optional L.decimal
                                            -- Parser.hs:900
```

Normative grammar for one interpolation item:

```
hole        = "{" expression [ "=" ] [ "," alignment ] [ ":" format ] "}"
alignment   = expression                       ; may be negative → left-align
format      = ("b" / "o" / "d" / "x" / "X") [ 1*DIGIT ]     ; precision, no "_"
```

This matches `doc/programming-guide.md:540`:
`{<interpolationExpression>[=][,<alignment>][:<formatString>]}` and
`tools/editors/vscode/GRAMMAR.md:323`.

Whitespace rules inside a hole (all verified by `test/syntax/interpolated-string.k`):

| Form | Result | Citation |
|---|---|---|
| `"{ intConst }"` | ok — `L.symbol "{"` and `expression` are lexemes | `:12-14` (`expected:0`) |
| `"{ intConst = }"` | ok — `equal` is a lexeme | `:24-26` (`expected:0`) |
| `"{intConst=, 10}"` | ok — `comma` is a lexeme | `:32-34` (`expected:0`) |
| `"{intConst=: d}"` | ok — `colon` is a lexeme | `:44-46` (`expected:0`) |
| `"{intConst=:d10 }"` | ok — `format` is `L.lexeme` so it eats trailing space before `}` | `:52-54` (`expected:0`) |
| `"{intConst=:d 10}"` | **error** — precision must be adjacent to the specifier | `:56-58` (`expected:1`) |
| `"{intConst=:}"` | **error** — the specifier char is mandatory after `:` | `:36-38` (`expected:1`) |

Ordering is fixed: `=` must precede `,align`, which must precede `:fmt` (`Parser.hs:896-898`).

**Brace escaping.** `{{` yields one literal `{`. Mechanism: the segment terminator is
`char '"' <|> try (char '{' <* notFollowedBy (char '{'))` (`Parser.hs:887`, `:893`), so a `{{`
is not a terminator; the text parser then consumes it via `char '{' *> MP.charLiteral`
(`Parser.hs:892`), i.e. it eats the first `{` and reads the second `{` as the character.
Verified: `test/syntax/interpolated-string.k:157-159` (`"{{}"` → `expected:0`, text `{}`),
`doc/programming-guide.md:572-573, 585`, `tools/editors/vscode/GRAMMAR.md:355-356, 368`.
`{{{expr}` = literal `{` then a hole.

**There is no `}` escape.** `}}` produces two `}` characters; `}` outside a hole is ordinary
text (`Parser.hs:892` has no `}` case). This differs from C#.

**Strings nest.** The `expression` inside a hole is the full expression grammar, which includes
string literals, which may themselves contain holes. Verified:
`test/syntax/interpolated-string.k:185-190` (`"{stringFun("{boolConst:b3}")}"` → `expected:0`)
and `:192-197`, `:199-204`. **A Rust lexer must therefore treat strings with a mode stack, not a
single regular expression.**

Other things legal inside a hole (verified): `<` and `>` (`"{ cast<uint32[2]>({0, 1}) }"`,
`:161-163`), `{ … }` initializer lists (`:206-212`), function calls (`:143-155`), full binary
expressions including `>>` (`library/processor/risc_v/trace.k:201`).

**Closing.** The string is closed by `L.symbol "\""` (`Parser.hs:883`), a lexeme — so trivia
after the closing quote is consumed there. The opening quote is a bare `char '"'`.

## 11. Operator precedence and associativity

Source: `Parser.hs:910-968`. The table is passed to
`Control.Monad.Combinators.Expr.makeExprParser` (`Parser.hs:834-835`), whose list is ordered
**highest precedence first**.

```haskell
opsTemplate = ops' [] []                                      -- Parser.hs:913
ops = ops' [ no_assoc Greater, no_assoc Less ]                -- Parser.hs:914-917
           [ binary ShiftRight, binary ShiftLeft ]            -- Parser.hs:918-920

no_assoc op = InfixN  (…)                                     -- Parser.hs:963
```

Notes a Rust implementer must reproduce:

- **`no_assoc Greater` and `no_assoc Less` (`Parser.hs:915-916`) put `>` and `<` at the SAME
  precedence level as `<=` and `>=`** — they are appended to that level's list via
  `++ relOps` (`Parser.hs:942`). All four relational operators, plus `==` and `!=`, are
  `InfixN`: `a < b < c` and `a == b == c` do not parse (the parser stops after one comparison
  and the remainder is unconsumed).
- **Bitwise operators bind tighter than logical ones**, and `&` > `^` > `|` > `&&` > `^^` > `||`.
  `^^` sits between `&&` and `||` — there is no C analogue.
- **Unary `-` binds tighter than `!` and `~`**, which bind tighter than the sizeof-family.
  Because `Control.Monad.Combinators.Expr`'s `Prefix` applies **at most one** prefix operator per
  level, the *only* legal unary stacking order is
  `[bitsizeof|bytesizeof|clog2] [ ! | ~ ] [ - ] term`.
  Consequently `!-x` parses, `-!x` does not; `!!x`, `~~x`, `- -x`, `!~x`,
  `bitsizeof bytesizeof x` all fail. (`!!x` and `~~x` are additionally blocked by
  `operator`'s `oneOf` guard, `Lexer.hs:262`.)
- `bitsizeof`/`bytesizeof`/`clog2` are **prefix operators, not calls** — the parentheses in
  `bitsizeof(x)` are just a parenthesized sub-expression. `bitsizeof x` is equally valid;
  verified: `library/processor/risc_v/internal/core.k:70`
  (`cast<uint1>(x >> (bitsizeof x - 1))`), `test/syntax/literals.k:129`
  (`static assert(bitsizeof x == 32);`), `doc/programming-guide.md:411-425`.
  Because they sit at level 3, `bitsizeof x - 1` means `(bitsizeof x) - 1`.
- The ternary is `TernR`, i.e. **right-associative**: `a ? b : c ? d : e` ≡
  `a ? b : (c ? d : e)`. It desugars to `Mux a [c, b]` (`Parser.hs:968`).
- Operands of `?:` are separated by `operator ":"`, which forbids a following `:` or `=`
  (`Lexer.hs:262`).

## 12. `<`, `>`, `<<`, `>>` — the tokenization question, answered

### 12.1 Does the reference produce `>>` as one token?

**There is no token stream, so the honest answer is: sometimes, depending on which parser runs.**
Concretely:

1. `>>` **is** consumed as one unit by `binary ShiftRight` = `operator ">>"`
   (`Parser.hs:918`, `Parser.hs:962`, `Lexer.hs:262`), which requires the two `>` characters to
   be **adjacent** and the next character to be **neither `>` nor `=`**.
2. `>>` **is** consumed as two units by two successive `rangle` calls, because
   `_angle ">"` only checks `notFollowedBy (char '=')` — it deliberately **does not** reject a
   following `>` (`Lexer.hs:270`, `Lexer.hs:273`). This is how `A<B<C>>` closes.
   Verified in real code: `library/test/internal/assert.k:59`
   (`reinterpret_cast<uint<bitsizeof T>>(expected)`), `library/codec/crc.k:68`
   (`cast<uint<max_bits>>(…)`), and a triple close at `library/numeric/float32.k:796`
   (`cast<tuple2<uint<Fbit>, uint<8>>>(exp2Value)`) and `library/numeric/float32.k:2022`
   (`pair<uint1, pair<bool, uint<1 + F1>>>`).
3. The two readings never compete, because inside `angles (…)` the operator table is
   `opsTemplate`, which **has no `>>` at all** (`Parser.hs:913`, comment at
   `Parser.hs:910-912`). So `>>` inside a template argument list can only ever be two closers,
   and `>>` in an ordinary expression can only ever be a shift.

Symmetrically for `<<`: `_angle "<"` accepts the first `<` of `<<` (it only rejects a following
`=`), so two adjacent `<` can open two template lists; and `operator "<<"` requires adjacency
plus a next character that is neither `<` nor `=`.

### 12.2 What the Rust "single `<`/`>` tokens + `glued_to_next` bit" must reproduce

Let `glued(t)` mean "no trivia (whitespace or comment) between token `t` and the next token".
The Rust lexer should emit `L_ANGLE` and `R_ANGLE` as **single-character tokens** and set the
`glued_to_next` bit. It may safely emit `LTEQ` (`<=`) and `GTEQ` (`>=`) as single tokens (see
rule 3 below). It must **never** emit `SHL`/`SHR` as lexer tokens; the parser composes them.

Reconstruction rules the parser must implement, each derived from a cited reference rule:

1. **Shift-right** = `R_ANGLE` with `glued_to_next`, immediately followed by `R_ANGLE`, where
   that second `R_ANGLE` is **not** glued to a following `R_ANGLE` and **not** glued to a
   following `EQ`. Derivation: `operator ">>"` = `string ">>" *> notFollowedBy (oneOf ">>=")`
   (`Lexer.hs:262`, `Parser.hs:918`, `Parser/Syntax.hs:98`).
   Therefore `a >>> b` and `a >>= b` are **parse errors**, not alternative readings.
2. **Shift-left**: symmetric, with `<` (`Parser.hs:919`, `Parser/Syntax.hs:97`).
3. **`>=` / `<=`**: safe to lex as one token. Every parser that could take the `>` alone
   refuses when the next character is `=`: `_angle` (`Lexer.hs:273`), `operator ">"`
   (set `{>,=}`), `operator ">>"` (set `{>,=}`). So a `>` glued to an `=` is *always*
   `GreaterEqual`, never a template close and never `Greater`.
4. **Template-list close (`rangle`)** = one `R_ANGLE` that is **not glued to a following `EQ`**.
   It **may** be glued to a following `R_ANGLE` — that is the nested-close case
   (`Lexer.hs:273` checks only `char '='`).
5. **Template-list open (`langle`)** = one `L_ANGLE` not glued to a following `EQ`; it may be
   glued to a following `L_ANGLE`.
6. **Comparison `>` (`Greater`)** = one `R_ANGLE` glued to **neither** a following `R_ANGLE`
   **nor** a following `EQ` (`operator ">"` forbids `oneOf ">="`, `Lexer.hs:262`).
   Symmetrically for `<`.
7. **Whitespace between the two closers is legal.** `A<B<C> >` parses (each `rangle` is a
   lexeme, `Lexer.hs:273`), but `a > > b` is **not** a shift (shift requires the literal
   two-character string, `Lexer.hs:262`). The `glued_to_next` bit is exactly what separates
   these two cases — this is why it is required.
8. **Comments count as trivia for gluing.** `A<B<C>/*x*/>` is two closers; `a >/*x*/> b` is not
   a shift, for the same reason as rule 7.

### 12.3 Also glue-sensitive (do not overlook)

The same adjacency machinery is needed for:

- `]]` / `[[` in the attribute-run separator, which uses `L.symbol "]]"`/`L.symbol "[["`
  (`Parser.hs:165`) — adjacent — while the enclosing `doubleBrackets` uses two independent
  `symbol "["` (`Lexer.hs:278-279`) — trivia allowed.
- `intN` (`string "int"` then digits, `Parser.hs:542`) — adjacent.
- `10i32` (number then suffix, `Parser.hs:908`) — adjacent.
- `:d10` (format specifier then precision, `Parser.hs:900`) — adjacent.
- `.field` in a designated initializer (`char '.'`, `Parser.hs:863`) — adjacent.
- module path dots (`char '.'`, `Lexer.hs:231`) — adjacent.

## 13. Proposed Rust `SyntaxKind` mapping

Design assumptions, matching the plan: SCREAMING_SNAKE token kinds; single-character angle
tokens; a `glued_to_next: bool` on every token; strings lexed in a **mode stack** (because holes
nest). Kinds marked *(mode)* are only produced inside the string mode.

## 14. Things a Rust implementer will get wrong without being told

Each entry has a `path:line`.

1. **`>>` is not a token** (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:273`). `rangle`
   only rejects a following `=`, so a single `>` closes a template even when glued to another
   `>`. Real code depends on triple closes:
   `third_party/kanagawa/library/numeric/float32.k:796`.
2. **`<` and `>` are non-associative comparisons at the *same* level as `<=`/`>=`**
   (`compiler/hs/lib/Language/Kanagawa/Parser.hs:915-916` combined with `Parser.hs:939-942`).
   `a < b < c` does not parse.
3. **`<=` and `>=` are still legal inside template arguments** but `<` and `>` are not
   (`compiler/hs/lib/Language/Kanagawa/Parser.hs:913` vs `Parser.hs:939-941`).
4. **Trailing `_` in a numeric literal is legal; leading `_` makes it an identifier**
   (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:148-149`; test
   `third_party/kanagawa/test/syntax/literals.k:96`).
5. **Exactly one `_` may follow a base prefix; two is a different parse.**
   `0x__1` is *not* an error — the hex branch fails, `decimal` matches the leading `0`, and
   `x__1` becomes an identifier (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:136`,
   `Lexer.hs:134`). Similarly `0b12` is `1` followed by `2`
   (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:148`).
6. **`10i` (suffix letter with no width) is a hard error, not `10` followed by identifier `i`**,
   because `optional` is not wrapped in `try`
   (`compiler/hs/lib/Language/Kanagawa/Parser.hs:906`).
7. **`10i32abc` lexes as `10i32` + `abc`** — the literal width has no boundary check
   (`compiler/hs/lib/Language/Kanagawa/Parser.hs:908`), unlike the type width
   (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:259`).
8. **`int0x1F` is neither a type nor an identifier** — `readMaybe :: Maybe Word` accepts Haskell
   base prefixes (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:241-242`).
9. **Escapes are Haskell escapes, not C escapes.** `\65` is decimal (`A`), `\x41` is hex,
   `\ESC`/`\^A`/`\&`/string-gaps exist, `\e` and `\{` do not
   (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:162`,
   `compiler/hs/lib/Language/Kanagawa/Parser.hs:892`).
10. **Interpolated strings nest arbitrarily deep** — a hole contains a full expression, which may
    contain another string (`compiler/hs/lib/Language/Kanagawa/Parser.hs:895`; test
    `third_party/kanagawa/test/syntax/interpolated-string.k:187`).
11. **`{{` escapes `{`, but `}}` does NOT escape `}`**
    (`compiler/hs/lib/Language/Kanagawa/Parser.hs:892-893`).
12. **The format precision must be glued to the specifier, but everything else in a hole may be
    spaced.** `"{x=:d 10}"` is an error while `"{x=: d}"` and `"{x=:d10 }"` are fine
    (`compiler/hs/lib/Language/Kanagawa/Parser.hs:900`; tests
    `third_party/kanagawa/test/syntax/interpolated-string.k:56`, `:44`, `:52`).
13. **Ordinary block comments nest; doc block comments do not**
    (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:103` vs `Lexer.hs:88`; test
    `third_party/kanagawa/test/syntax/doc-comments.k:135`).
14. **Once a doc-comment run starts, every following comment is absorbed into it — including
    `//<` comments and plain `//` comments** (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:82-84`;
    test `third_party/kanagawa/test/syntax/doc-comments.k:172-179`).
15. **With `--parse-docs`, a doc comment in a position with no `notedWithDocs` wrapper is a hard
    parse error**, because `whitespaceNonDoc` refuses to skip it
    (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:110-111`; test
    `third_party/kanagawa/test/syntax/doc-comments.k:224-230`).
16. **Doc comment text retains its `|`/`<` prefix character**; the consumer strips it
    (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:87`;
    `third_party/kanagawa/tools/sandcastle/lib/Sandcastle/DocGen.hs:1030`).
17. **`templateQualifier` uses `L.symbol "template"` with no word boundary**, so an identifier
    beginning with `template` is split: `templateFoo` parses as the `template` disambiguator
    followed by identifier `Foo`
    (`compiler/hs/lib/Language/Kanagawa/Parser.hs:646`). A token-based Rust lexer will *not*
    reproduce this. No corpus file exercises it (see §16 Q9).
18. **Only one prefix operator applies per precedence level**, so `-!x`, `!!x`, `!~x`,
    `bitsizeof bytesizeof x` are all rejected while `!-x` and `clog2 !-x` are accepted
    (`compiler/hs/lib/Language/Kanagawa/Parser.hs:922-930`).
19. **`unrolled_for` is reserved but has no grammar** — it cannot be an identifier and cannot be
    used (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:215`).
20. **`assert` is contextual, not reserved** — `static assert(…)` is two lexemes with trivia
    allowed between them, and `assert` remains a usable identifier
    (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:256`,
    `third_party/kanagawa/library/test/internal/assert.k:22`).
21. **Module names have a laxer identifier grammar than everything else** — `-` is legal
    (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:231-233`;
    `third_party/kanagawa/library/mini-base.k:12` declares `module mini-base`).
22. **`#` is never a legal character outside comments/strings** — `hash` is dead code
    (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:288`).
23. **Identifiers are Unicode**, numbers are ASCII-only
    (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:222-225` vs `Lexer.hs:138-141`).
24. **Float literals are single precision** (`Parser/Syntax.hs:352`) while integer literals are
    arbitrary precision (`Parser/Syntax.hs:349`).
25. **Type widths and literal widths are Haskell `Int` with no range check**
    (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:259`,
    `compiler/hs/lib/Language/Kanagawa/Parser.hs:908`); megaparsec's `decimal` performs no
    overflow detection, so `uint99999999999999999999` silently wraps.
26. **`++`/`--` are statements, accepted in prefix *and* postfix position, never expressions**
    (`compiler/hs/lib/Language/Kanagawa/Parser.hs:607-614`).
27. **There is no `<<=` or `>>=`** (`compiler/hs/lib/Language/Kanagawa/Parser.hs:618-628`).
28. **`[[a]] [[b]]` requires adjacent `]]`/`[[` but `[ [a] ]` is legal**
    (`compiler/hs/lib/Language/Kanagawa/Parser.hs:165` vs
    `compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:279`).
29. **`skipBraces` counts raw braces and ignores strings and comments**
    (`compiler/hs/lib/Language/Kanagawa/Parser/Lexer.hs:122`).
30. **`float` is a library alias, not a keyword**
    (`third_party/kanagawa/library/type/cstddef.k:10`).

## 16. Open questions

Each names the probe program that settles it. Probes are `.k` files runnable through the syntax
harness (`test/syntax/syntax-test.py`, invoked per `test/syntax/CMakeLists.txt:54-74`, with
`expected:<exit-code>` markers).

**Q1 — megaparsec library predicates.** `space1`, `hspace`, `letterChar`, `alphaNumChar`,
`L.decimal`, `L.float`, `L.symbol`, `L.skipBlockCommentNested` are library code
(`megaparsec >= 9.0`, `compiler/kanagawa.cabal:108`) and not present in this tree; no GHC/cabal
toolchain is installed on this machine. Their behavior above is taken from the megaparsec 9
documentation.
*Probe:* pin megaparsec to the exact version cabal resolves, and diff the Rust lexer's
character classes against `Text/Megaparsec/Char.hs` and `Text/Megaparsec/Char/Lexer.hs`. In
particular confirm whether `space1` accepts `U+00A0` and whether `hspace` is
`isSpace c && c /= '\n' && c /= '\r'`.
*Fast Kanagawa probe for `space1`:* a file containing `const auto x =\u{00A0}1;` — `expected:0`
if `U+00A0` is whitespace.

**Q2 — the `readMaybe :: Maybe Word` rejection set.** The claim that `int0x1F`, `int0b11`,
`uint0o7` are rejected as identifiers rests on GHC's `Text.Read.Lex.lexBaseChar` accepting
`x/X/o/O/b/B`, which is not in this tree.
*Probe:* `const auto int0x1F = 1;` and `const auto int0b11 = 1;` and `const auto int1e5 = 1;`.
Expected under this spec: `expected:1`, `expected:1`, `expected:0` respectively.

**Q3 — exact escape set accepted by `L.charLiteral`.** The Haskell-report escape list above,
including `\&`, string gaps, `\^X` controls, and the 10-character look-ahead bound, is from
megaparsec/`Data.Char.readLitChar` documentation, not from this tree. The corpus exercises only
`\n \t \r \" \\`.
*Probe:* `inline void f() { println("\65\x41\o101\ESC\^A\&x"); }` — `expected:0` if all are
accepted. And `inline void f() { println("\e"); }` — `expected:1` expected.
Also probe the look-ahead bound: `"\1114111"` (7 digits) vs `"\11141110"`.

**Q4 — doc line comment at EOF without a trailing newline.** `lineComment` requires `char '\n'`
(`Lexer.hs:87`).
*Probe:* a `--parse-docs` file whose final bytes are `//| doc\nstruct Foo{}\n//< post` with **no**
final newline. Expected under this spec: `expected:1`.

**Q5 — CRLF handling of doc text.** Does `\r` end up inside the captured doc string
(`Lexer.hs:87`)?
*Probe:* a CRLF-encoded `--parse-docs` file with `//| doc` and a Sandcastle run
(`tools/sandcastle`) checking whether the emitted Markdown contains a stray CR.

**Q6 — no boundary check after a literal width.**
*Probe:* `const auto x = 10i32abc;` — under this spec this is `10i32` followed by identifier
`abc`, so the statement is a syntax error (`expected:1`) but with an "unexpected identifier"
message rather than "invalid literal". Compare the error text against a Rust implementation that
lexes `10i32abc` as one bad token.

**Q7 — bare `i`/`u` suffix.**
*Probe:* `const auto x = 10i;` — under this spec `expected:1` (hard error), and specifically
*not* parsed as `10` followed by identifier `i`. Contrast with `const auto x = 10 i;`.

**Q8 — underscores and exponents in float literals.**
*Probe:* `float32 a = 1_0.5;`, `float32 b = 1.5e3;`, `float32 c = 1e3;`, `float32 d = 1.;`,
`float32 e = .5;`. Expected under this spec: `1`, `0`, `0`, `1`, `1`.

**Q9 — the `templateFoo` splitting bug.** `L.symbol "template"` has no word boundary
(`Parser.hs:646`). No corpus file has an identifier starting with `template` in an
expression/type position (all such strings in `library/`+`test/` are module paths or comments).
*Probe:* `inline void f() { const auto templateFoo = 1; }` where `Foo` is also declared. Under
the reference this should resolve to `Foo` with `forceTemplate` set (probably an error message
mentioning `Foo`, not `templateFoo`). Decide explicitly whether the Rust lexer reproduces this
or deliberately diverges; recommend diverging and recording it as a known incompatibility.

**Q10 — `>` glued to `=` inside template arguments.** §12.2 rule 3 asserts `>=` may always be
lexed as one token. This holds for every parser in `Lexer.hs`/`Parser.hs`, but no corpus file has
a template list ending immediately before an `=`.
*Probe:* `template <auto N> using A = uint<N>; const auto x = A<4>= 1;` (i.e. `>` glued to `=`
where a template close is wanted). Under this spec the reference reads `A < (4 >= 1)` and errors;
confirm the Rust lexer produces the same diagnostic shape.

**Q11 — attribute names matched without word boundaries.** `L.symbol (show x)`
(`Parser.hs:171-177`) would match the prefix of a longer word.
*Probe:* `[[asyncx]] void f() {}` — expected `expected:1` either way, but confirm the reference
does not silently accept `[[async]]` + stray `x`.
