# Known divergences from the reference compiler

Deliberate or accepted differences between `kgrust` and the Haskell/C++
reference, with the evidence for why each is acceptable. Anything here is a
*known* difference; an unknown one is a bug.

The correctness bar for this project is **test-equivalent**, not byte-identical:
the same accept/reject decision and functionally equivalent RTL. Every entry
below is judged against that bar.

## Lexer

| # | Divergence | Status |
|---|---|---|
| 1 | **`\&` (empty escape) and string gaps** (`\` whitespace `\`) are accepted. megaparsec's `charLiteral` delegates to `base`'s `readLitChar`, whose `readEsc` has no case for either, so the reference rejects them. | **Wider than the reference.** Neither form occurs anywhere in the 480-file corpus. Accepting more than the reference can only turn a reference *reject* into an *accept*, so it is visible to `expected:1` assertions — none of which use these forms. |
| 2 | **`int0x10` / `uint0o7` are usable identifiers here.** GHC's `readMaybe :: Maybe Word` accepts `0x`/`0o` forms, so the reference's `intType` check (`Parser/Lexer.hs:241-243`) reserves them, while its `intSuffix` (`:258-259`) cannot parse them — making such a name unusable either way. | **Accepted.** Both compilers reject any *use*; only the diagnostic differs, and both are `Error 1`. |
| 3 | **Comments inside a string interpolation** are not understood by the string scanner: `"{ /* \" */ x }"` would end the string early. | **Accepted.** Does not occur in the corpus. Fix if a real program ever needs it. |
| 4 | **Unicode identifier classes.** `char::is_alphabetic` is Unicode's Alphabetic property, marginally wider than GHC's `isAlpha` (it also admits `Nl` and `Other_Alphabetic`). | **Accepted.** Wider, as in #1. |
| 5 | **Doc-comment grouping is the parser's job, not the lexer's.** `docComment` (`Parser/Lexer.hs:81-88`) checks for the `\|`/`<` marker on the *first* comment of a run and then swallows every following comment into the same doc comment, so `//\| line one` + `// line two` is **one** doc comment. A token has exactly one kind, so the lexer emits `DOC_LINE_PRE` then `LINE_COMMENT`. | **By design.** The consumer regroups a maximal whitespace-separated run of comment tokens under whichever doc kind opens it. This pattern occurs 566 times in `library/` alone, so `kg-fmt` and `kg-doc` must both honour it. Pinned by `doc_comment_continuation_lines_stay_plain`. |
| 6 | ~~Exponent-only floats (`1e5`) lex as an integer plus an identifier.~~ | **Fixed.** megaparsec's `L.float` has a second branch, `decimal_` followed by a bare exponent. Found by adversarial verification; regression test `exponent_only_floats_are_floats` also pins that `0x1e5`, `0b1e5` and `0o7e2` are *not* floats. |

## Parser

| # | Divergence | Status |
|---|---|---|
| 7 | **No symbol table during parsing.** The reference decides "is `Foo` a type?" and "is `Foo<X>` an instantiation?" with `findSymbol` mid-parse. Here both are bounded token scans (`grammar/lookahead.rs`), and anything that genuinely needed a name lookup becomes a name-resolution diagnostic later. | **By design**, and invisible to conformance: every reference frontend error is `Error 1` (`Parser/IO.hs:114`), so only the accept/reject decision is observable. See `docs/architecture.md`. |
| 8 | **Errors are recovered from, not fatal.** The reference stops at the first parse failure. | **By design.** A language server must describe a file that is halfway through being typed. The `kanagawa` compat binary still reports and exits 1. |
| 9 | **Residual angle ambiguity: `a < b && c > d`.** This is simultaneously a valid chained expression and a valid declaration of `d` with type `a<b && c>`. The reference resolves it by asking its symbol table whether `a` names a template; `kg-parser` has no symbol table at parse time (see #7) and lets the *declaration* reading win. The closing-`>` follow-set (`CANNOT_FOLLOW_TEMPLATE_ARGS`, `grammar/lookahead.rs:82`) is a deny-list — an allow-list was tried first and broke `bitsizeof S<uint6> - 2` (`test/logic/test_cases_24.k:153`), which is a template instance used as an operand. | **Accepted.** No file in the corpus depends on the expression reading; acceptance is 357/357 and conformance 2681/2681 with the declaration reading (`scripts/gates.sh`, 2026-10-11; 355/355 and 1832/1832 when this entry was written, in August). Revisit if name resolution ever wants to re-decide this — the CST records enough to re-parse the span. |
| 10 | **`templateFoo` is one identifier here.** `templateQualifier` uses megaparsec's `L.symbol "template"` (`Parser.hs:646`), which has no trailing word-boundary check, so the reference reads `templateFoo` as the `template` disambiguator followed by the identifier `Foo`. A token-based lexer cannot reproduce this without special-casing a keyword prefix. | **Deliberate divergence.** The reference behaviour is a bug that no program could rely on intentionally; reproducing it would mean the lexer could not tokenise identifiers independently of parser state. The corpus does contain identifiers beginning with `template` (`template_instance_identifiers`, `template_template_test`, `templates`), but every one of them sits in a position parsed by plain `identifier` or `dotSepName` — import paths (`Parser.hs:179-183`), module-exposure lists (`:186`) and class names — never by `prefixedScopedNameAndSymbol` (`:652-653`), the sole caller of `templateQualifier`. So the split is unobservable on the corpus, and `kg-parser` agrees with the reference on all of them. |

| 12 | **`statement` vs `statementOrDecl` is not enforced.** The reference admits a declaration only where `statementOrDecl` is reachable (`Parser.hs:471-479`); a declaration as the *body* of an `if` or a `reorder` is rejected. `kg-parser` accepts `if (c) uint8 x;` and `reorder bool x;`. | **Accepted for now, and visible.** `test/syntax/statement.k:4-17` marks these `expected:1`, so they sit in the conformance harness's *undecidable* bucket rather than counting as passes — the scoreboard is not being flattered. Enforcing it costs a second dispatch and degrades recovery in half-typed bodies, which is the wrong trade for an editor before the semantic passes exist. Name resolution can reject them later; the error is `Error 1` either way. |
| 13 | **Postfix is one uniform loop**, so `f(x)[0]` and `f().g()` parse. The reference confines the access chain to its `value`/`lvalue` productions (`Parser.hs:783-819`). | **Wider in the parse, closed after it (2026-10-10).** The claim this row made — that anything extra is rejected at name resolution or type checking — was false: `(x)[i];`, `y = arr()[0];`, `(s).a`, `st().a`, `(one)(1)` all compiled here (difffuzz 2026-10-10 [47], [48], [50]). `pass_0_postfix_on_a_name` (`kg_db::passes::early_normalization`) now rejects an index or a member access whose base is not a name, a member or an element, and a call whose callee is not a name or a method — at the postfix token, where the reference's own error lands in an expression (`kg-oracle --errors`); in a statement the reference's lands on the name, and the `errors` gate books the pair to #7. The CST keeps the uniform loop, for the editor. |
| 14 | **`DEFAULT_INIT` has no node kind.** `default = expr;` (`Parser.hs:314`) is valid — 7 occurrences across the corpus — and is emitted as a bare `ERROR` node carrying no diagnostic. | **A known gap, fenced by a test.** `the_only_error_nodes_in_whole_programs_are_default_initializers` asserts these 7 are the *only* `ERROR` nodes any whole program produces, so the exception cannot grow silently. Losslessness and acceptance are unaffected; the fix is one `SyntaxKind` and one production. |
| 15 | ~~**Interpolated strings stay one `LITERAL` token.**~~ | **Closed 2026-09-22.** The lexer now splits a string at its holes — `STRING_TEXT` up to a hole, the hole's own code tokens, `STRING_END` after the last — and the parser builds `INTERPOLATED_STRING` / `INTERPOLATION` / `FORMAT_SPEC`, each hole an ordinary expression. A string with no hole is still one `STRING`. It was never the event stream that forbade it (a *lexer* that splits needs no split event); it was the lexer declining to know where a hole ends, which brace counting and a mode stack settle. Two residues: a format spec is kept as the tokens before the hole's `}` and judged by pass 0's character grammar, and an *attribute* string with a `{` — `stringLiteral` reads the brace as text (`Parser/Lexer.hs:161-162`) — is one `LITERAL` over the split pieces; no corpus attribute writes one. The IR followed the same day: `Exp::Interpolated` carries the reference's segments with the holes as children, so rewrites reach them and a copy prints them substituted. |

## CLI

| # | Divergence | Status |
|---|---|---|
| 11 | ~~**`kanagawa` never exits 0.**~~ | **Closed.** The compat binary runs the whole frontend and walks the program through the reference's backend (`kg_ptbridge`, in a worker), and exits with the reference's code — `cargo xtask backend` grades the first `Error N` and the exit code per program, 3215/3270 agreeing on 2026-09-27 — except that a backend crash is 3 (#33). | 33 | **A backend that throws or faults is exit 3 and a message, not a dead process.** The reference runs `libkanagawa-backend` in its own process, so a C++ exception no one catches — anything out of a `Parse*` call; only `InitCompiler` and `Codegen` catch (`parse_tree.cpp:6285`, `kanagawa.cpp:50`) — is `std::terminate`, `SIGABRT`, 134 to a shell (`docs/spec/cli.md` §7). `kanagawa` and `kg build` walk into a recording and replay it into the library in a worker process (`kg_ptbridge::isolate`); a worker that dies is reported on stderr, naming the call it threw out of, and the run exits **3**. | **Deliberate (AUDIT D6).** In-process, the same exception unwound into Rust — undefined behaviour, observed as `fatal runtime error: Rust cannot catch foreign exceptions` and an abort that named nothing. 3 is neither of the codes `syntax-test.py` accepts (`:158-163`), so an assertion over a crashing program fails whatever it expected, as it does against the reference's 134. Cost: one process spawn and one serialized walk per build — measured 2026-09-23 as +1 ms on a syntax snippet and +16 ms (1.3%) on `library/numeric/fixed.k`, the largest walk that reaches `Codegen`; the backend's own stdout, stderr and files are byte-identical over 2,917 of 2,922 syntax programs, the other five being the two crashes and three programs the walk declines, which no longer reach the backend (AUDIT §4.4) and so no longer print the `Error 3` a half-built program earned. | 34 | **`cmdargs`' own error text, two help formats, the version.** An argv this binary refuses is refused with the reference's exit code (1) on its stream (stderr), worded its own way and prefixed `kanagawa: ` — `Unknown flag: --x` gains a line naming the mode that has it, `Ambiguous flag` lists `--names`, a bad value names the flag — where `cmdargs` prints `Ambiguous flag '--max', could be any of: …` and `Could not read as type Int, "x"` (`Explicit/Process.hs:65-131`). `--help` answers at the flag, where `cmdargs` finishes the argv first and lets a later error win. `--help=bash` and `--help=zsh` are refused: they print a completion script that calls the program back under `CMDARGS_COMPLETE`, which this binary does not answer. | 35 | **`--frontend-passes` below 19, and `--template-passes` below 9 under a counted `--template-iterations`, are refused** (exit 1, stderr, by name). The reference runs that prefix of its pass lists (`Frontend.hs:38`, `Template.hs:62-64`) and hands the backend a tree desugared that far — its own backend then often dies of it (`--frontend-passes=5` on a two-function program: `Prelude.undefined`, `ParseTree.hs:164`, probed 2026-10-09). This compiler's passes and rounds run fused (`kg_hir::rewrite::round_prefix`), so neither prefix is a state it holds. Every value that bounds nothing — 19 or more, or `--template-passes` without a count — runs as the default. | **By design.** A debugging aid for the reference's own frontend; nothing in-tree passes either (`docs/spec/cli.md` §8.10). `--template-iterations` itself is honoured: it is the loop's round bound (`kg_cli::legacy::run::pass_budget`). |
| 36 | **`--dump-parse`, `--dump-types` and `--dump-program` print nothing**, and say so on stderr; the compile goes on. The reference prints GHC's `show` of its own syntax tree (`prettyExp`, `PrettyPrint.hs:22-34`; `Main.hs:81-84,92-93`) — every constructor of its `ExpF` and every field, including state this compiler's IR does not keep — which no faithful port short of that type could produce. | **Accepted.** An internal format, not a contract; nothing in-tree reads it. `--dump-ir`, `--dump-opt` and `--dump-memory-metadata` are the backend's and work. |
| 37 | **`pretty` and `--dump-source` are not ported, by decision** (owner, 2026-10-09): both are the reference's pretty printer (`PrettyPrint.hs`), and `kg fmt` is this project's formatter. `pretty` parses, prints the parse's errors as the reference does, and otherwise exits 1 with a refusal on stderr — never source text on stdout; `--dump-source` is said on stderr and the compile goes on. | **By design.** Its flags are still accepted and its help is the reference's. |

### Why #11 was the gate on the whole L1 strategy

*History: #11 is closed and the experiment below runs — `cargo xtask
repoint`, 51/72 on 2026-09-27. Kept for the reasoning.*

`test/syntax/syntax-test.py:103-106` invokes the compiler as

```
kanagawa [options] --place-iterations=1 --import-dir <helperdir> <file>
```

with **no `--backend`**. The reference's default is `backend = None`, which its
own help text describes as "produce metadata only"
(`compiler/hs/app/Options/CmdArgs.hs:75`). So every one of the 2,516 live syntax
assertions is a *frontend-only* run, and `syntax-test.py:158` requires exit 0
for each of the 1,768 that expect no error.

The consequence is worth stating plainly: **the repoint experiment does not need
the backend.** Once name resolution and type checking land — the end of Phase 3,
not Phase 4 — pointing `kanagawa::exe` at this binary should make
`ctest -R '^syntax\.'` green against the real upstream harness, using upstream's
own runner rather than our reimplementation of it. That is the strongest
possible check on `xtask conformance` itself, because it tests the scoreboard
against the thing the scoreboard was written from.

Until then the exit code must stay 1. The order matters: make the frontend
correct, *then* let it claim success.
